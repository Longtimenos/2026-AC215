Lecture 1 · Foundations

Why any of this exists: environments, machines, and the cloud
Sources: L01 Introduction; Tutorial 0 (ac215-setup); Tutorials 1–2 (simple-translate, manual install and uv); recap slides in L02.

What MLOps is
MLOps = building ML/DL models + application development + operations, run as one unified practice rather than three teams throwing artifacts over a wall. The course splits the work into three task families:

Area	Tasks
Machine / Deep Learning	Data collection, model exploration and selection, training, evaluation, distillation, compression
Application development	APIs and model serving, ML integration, web and mobile apps, edge-device deployment, automation scripts
Operations	Provisioning and managing servers, keeping the app up, CI/CD, continuous data and model training, monitoring, versioning, workflow management
The same stack read by role: data engineers (Hadoop, Spark, Kafka, Airflow, databases), data scientists (dev environments, training frameworks), software engineers (version control, containerization, frontend), systems engineers (cloud infrastructure, orchestration, deployment automation).

The problem every later tool solves
One app, several developers on macOS, Windows and Linux, plus a build server and a production server on yet another OS version. Without containers each machine needs its own OS-specific install of Python, Node.js, C++ toolchains and system libraries, and “works on my machine” is the default failure. The course walks the ladder: system install → virtual environment → container, and separately your laptop → a cloud VM.

Virtual machines and hypervisors
A virtual machine is a full computer in software: virtual CPUs, virtual memory, virtual drives, and its own complete guest operating system, running on top of a hypervisor. The hypervisor is the software layer that creates, manages and schedules VMs and presents virtualized hardware to each of them. The physical machine's OS is the host OS; the OS inside each VM is a guest OS, and different VMs can run completely different guest operating systems on one host.

Note — Definition to memorize

Hypervisor: a software layer that creates and manages virtual machines, each running its own full guest OS on virtualized hardware. It is not a kernel module the guest loads, not a container runtime, and not a user-space instruction-by-instruction emulator.

VM pros	VM cons
Control	Full autonomy — complete control of OS and apps, like a physical server	—
Isolation	Very secure; isolated environment minimizes risk of intrusion; guest cannot affect host	—
Cost	Lower cost when you need full OS functionality; many OSes on one machine	—
Cloud	Offered by every major cloud provider as on-demand server instances	—
Resources	—	Resource intensive — consumes the host's hardware
Portability	—	VMs are large files, hard to move between systems
Overhead	—	Extra resources to run the hypervisor and manage multiple OSes; slow startup
Desktop virtualization tools named in the course: VirtualBox, VMware, Parallels. Cloud VMs: GCP Compute Engine instances, AWS EC2.

Virtual environments, uv, and what activation actually does
A Python virtual environment is an isolated Python installation-ish directory: its own site-packages/ for third-party libraries, links to a Python interpreter, and activation scripts. It isolates Python packages only — it shares the host OS and kernel, so it cannot fix OS-level or system-library differences.

Note — The PATH mechanism — the most quizzed detail

source .venv/bin/activate does four things: (1) prepends .venv/bin/ to PATH so python and pip resolve to the environment's binaries; (2) sets VIRTUAL_ENV=/path/to/.venv; (3) changes the shell prompt to show the env name, e.g. (simple-translate) $; (4) defines a deactivate shell function that undoes the first three.

So after activating, which python prints a path inside the virtual environment — because activation put the env's bin/ earlier on PATH, not because the system interpreter was replaced, removed, or patched. You use source (not ./activate) because all of this must happen in the current shell.

Tool	What the course says
virtualenv / venv	Embedded in Python by default; packages managed with pip; virtualenv your_env_name
conda	Embedded in Anaconda; supports both conda and pip; ships data-science packages; conda create --name your_env_name python=3.7
pipenv	Built on virtualenv, fixes its shortcomings; separates dev vs production dependencies; tracks them in Pipfile + Pipfile.lock (the AWS track of the course uses pipenv where GCP uses uv)
uv	The course's tool (Astral). Fast; creates the env, resolves and installs packages, and can install Python itself. Manifest pyproject.toml, lock file uv.lock, environment directory .venv/

PEP 668, --break-system-packages, and apt vs apt-get
Modern Debian/Ubuntu mark the system Python as externally managed (its packages belong to the OS, via apt). pip therefore refuses to modify it; --break-system-packages overrides that protection. Tutorial 1 uses it deliberately as a demonstration of the wrong way; Tutorial 2 replaces it with uv.
apt-get is the older, stable, scriptable interface with predictable output — the one to use in Dockerfiles and CI. apt is the friendlier interactive wrapper (progress bars, colors). Either is fine typed at a VM shell.
Virtual environments vs virtualization vs containerization
The single most repeated diagram in the course, bottom-up:

Virtual environments	Virtual machines	Containers
Stack	Infrastructure → OS → Python → venv per app (libs only)	Infrastructure → hypervisor → one guest OS per VM → bins/libs → app	Infrastructure → OS → container engine (Docker) → bins/libs → app
Isolates	Python packages	Whole machine, including the kernel	Processes, filesystem, network — via kernel namespaces
Own OS kernel?	No	Yes — a full guest OS each	No — shares the host kernel; ships only the user space it needs
Weight / startup	Tiny / instant	GBs / slow boot	MBs / near-instant
Fixes OS-level differences?	No	Yes	Yes
The container wish list that motivated the jump: automated setup (install the OS-level libraries and the Python environment for you), isolation (complete separation from the host, consistent run-time environment), resource efficiency (minimal CPU, memory, disk), quick startups (near-instantaneous).

Lecture 2 · Containers I

What a container is, and how Docker builds one
Sources: L02 Containers I; Tutorials 3–4 (simple-translate with Docker, then on a VM).

What a container is
“A container is a program that runs on your host machine — like a mini computer inside it. It shares the host's CPU, memory and disk, but keeps its own OS view, file system and network. It packages code with its dependencies, so it runs the same no matter where it's deployed.”

The precise version: a container is the user space of an OS. Each container carries the minimum code needed to run its program and leverages the host's kernel (and host user-space facilities) to do the actual work. That is what makes containers small and fast, and why they are not VMs: no guest kernel, no guest OS boot.

The OS splits into the kernel (low-level access to hardware) and user space (programs outside the kernel). Docker's engine lives in user space; the isolation it relies on lives in the kernel.

Linux namespaces — the isolation half
Namespace: a Linux kernel feature that creates isolation between system components, giving a process (or group of processes) its own separate view of system resources. A process placed in a namespace can see and interact only with the resources inside it.

Namespace	What it isolates — and the course's example
PID	Process IDs. Each namespace starts its own numbering at 1, so processes in different containers can share a PID. Example: Nginx is PID 1 in one container, MySQL is PID 1 in another; on the host they are global PIDs 345 and 678.
Mount	The filesystem view: mounted disks, mount points, directories. Example: two containers both mount /data, one from Drive_A and one from Drive_B; neither is aware of the other's mount.
Network	Its own isolated sub-network: IP addresses, routing tables, firewall rules. Example: several containers can use the same IP address without interfering. This is also why localhost inside a container means that container.
IPC	Inter-Process Communication — isolates process communication and shared memory per namespace.
UTS	UNIX Timesharing System — lets each namespace define its own hostname / localhost.
User	Isolates users and groups. Even a process running as root inside the container has non-root privileges on the host.
cgroups — the resource half — and the security extras
Feature	Job	Do not confuse with
Namespaces	Isolation: what a container can see	cgroups (which limit what it can use)
cgroups (control groups)	Limitation and management of system resources: CPU, memory, disk I/O, network bandwidth. Enable efficient utilization, make containers lightweight vs VMs, and stop one container from bringing the system down by exhausting a resource	AppArmor/SELinux — cgroups are resource management, not access control
seccomp (secure computing mode)	By default containers get a reduced privilege set: 44 of the 300+ system calls are blocked. Keeps containers isolated and unable to control the host	—
AppArmor / SELinux	Additional security modules that restrict use of files, directories, sockets and other processes, preventing a container from touching core system components	cgroups (resources)
Blocked-syscall examples from the slides: reboot (a container could reboot the host) and quotactl (a container could change disk quotas and affect the host, other containers and VMs). A container is unlikely to need root privileges, since those tasks can be executed by the host — only the absolutely necessary information is passed into the container.

Why Docker works on macOS and Windows at all
Docker containers rely on Linux kernel features. So both non-Linux hosts spin up a stripped-down Linux VM that translates syscalls from the Docker daemon to the native kernel:

macOS: HyperKit — a virtualization technology. (Newer Docker Desktop builds use Apple's Virtualization framework, but HyperKit is the name on the slide.)
Windows: WSL2 — a custom-built Linux kernel integrated with Windows. It spins an even thinner Linux VM, which lets it run native Linux programs.
Watch out — Exam angle

“Containers are lightweight because they don't need a VM” is only true on Linux. On a Mac or Windows box there is a VM underneath — one thin shared VM for the whole engine, not one per container.

Image vs container (and the vocabulary list)
A Dockerfile is a text file → docker build produces an image → docker run produces a container. The image is a template/blueprint holding the configuration needed to instantiate a running container.

Recipe analogy: Dockerfile = the handwritten recipe; image = a pre-assembled ingredient kit (meal-delivery box); container = the final cooked dish.
OOP analogy: image = the class; container = an instance of that class. Many containers can run from one image, and they need not behave identically — run-time arguments (overriding CMD) make them different.
Term	Definition from the vocabulary slide
Docker image	The basis of a container; represents a full application. “How you store your application.” Read-only
Docker container	The standard unit in which the application service resides and executes. “How you run your application.”
Registry service	Docker Hub or Docker Trusted Registry — cloud or server-based storage and distribution for your images
Docker engine	Creates, ships and runs containers, deployable on a physical or virtual host: locally, in a datacenter, or at a cloud provider
Dockerfile	A text document with commands describing how to create an image
Dockerfile instructions
Instruction	What it does
FROM	Specifies the base image (e.g. python:3.12-slim-bookworm, alpine, ubuntu). A platform image has no parent and defines the runtime environment
RUN	Executes commands while building. Each RUN creates a new layer
COPY	Copies files from the build context into the image. COPY --chown=app:app . ./ sets ownership as it copies
ADD	Like COPY, but can also handle URLs and auto-extract compressed files
ENV	Sets environment variables in the image; available to later build steps and at run time
ARG	A build-time variable only. Not present in the running container. May show up in build history/metadata — never put secrets here
WORKDIR	Sets the working directory for the following RUN, CMD, ENTRYPOINT, COPY and ADD instructions
USER	Switches the user for subsequent steps and at run time (the tutorials create a non-root app user)
ENTRYPOINT	Sets the default executable, making the container behave like a standalone application
CMD	Sets default commands/parameters at container startup — overridable by docker run arguments
EXPOSE	Documentation only. It publishes nothing; you still need -p
RUN --mount=type=secret	Mounts a secret for one build step only (needs # syntax=docker/dockerfile:1 as the first line)
Reference: docs.docker.com/engine/reference/builder

ENTRYPOINT vs CMD — the rule, in one table
Exec form: ENTRYPOINT ["executable","arg"] and CMD ["arg"]. The final command is ENTRYPOINT + (run arguments, if any, else CMD). Run arguments replace CMD; they are appended to ENTRYPOINT. To replace ENTRYPOINT itself you need the --entrypoint flag.

FROM ubuntu:latest
RUN apt-get update
ENTRYPOINT ["/bin/echo", "Hello"]
CMD ["world"]

$ docker build -t hello_world_cmd -f Dockerfile .
$ docker run -it hello_world_cmd            → Hello world
$ docker run -it hello_world_cmd Pavlos     → Hello Pavlos
You run	Command executed	Why
docker run greeter	/bin/echo Hello world	No argument given, so CMD supplies world
docker run greeter Pavlos	/bin/echo Hello Pavlos	The run argument replaces CMD and is appended to ENTRYPOINT
docker run --entrypoint /bin/bash greeter	/bin/bash	--entrypoint overrides ENTRYPOINT; the CMD is dropped too unless you re-supply args
docker run -ti --entrypoint /bin/bash greeter -c "ls"	/bin/bash -c "ls"	Trailing args still append to the new entrypoint
Watch out — Wrong answers to recognize

<span class="no">×</span> “CMD is baked in and run arguments cannot change it” — false, overriding CMD is precisely what run arguments do.
<span class="no">×</span> “A run argument replaces the whole startup command, ENTRYPOINT included” — false, that is what --entrypoint is for.
<span class="no">×</span> “The argument is appended after both ENTRYPOINT and CMD” (→ Hello world Pavlos) — false, CMD is replaced, not kept.

The course's own use of the pair: get a shell that is already inside the uv venv.

ENTRYPOINT ["/bin/bash"]
CMD ["-c", "source /home/app/.venv/bin/activate && exec bash"]
Layers, the build cache, and why any of it matters
When you run docker build, the daemon reads the Dockerfile and creates a layer for every instruction. Layering, top to bottom:

Container — the application sandbox. When you launch a container, a writable layer is added on top of the image.
Layered images — read-only static snapshots; each depends on one or more parent images.
Platform image — defines the runtime environment, packages and utilities; an image with no parent.
Why layers rather than one big blob: efficiency (reuse common layers across images, saving storage and speeding creation), incremental updates (update only the changed layer — less time and bandwidth to deploy), cache utilization (Docker caches layers; unchanged steps make later builds faster), modularity (break complex setup into debuggable pieces), security (smaller attack surface per layer, easier vulnerability scanning).

Note — The caching rule — know this cold

A layer is reused when its inputs are unchanged (the instruction text, and for COPY/ADD the contents of the files copied). Change a layer and you invalidate that layer and every layer after it. Nothing about this is specific to RUN vs COPY: a dependency-install RUN stays cached after you edit source code because its inputs did not change, while the COPY of your source and all following steps re-run because the copied contents changed.

Second build of an unchanged Dockerfile, as it appears in terminal output:

=> CACHED [2/4] RUN set -ex; apt-get update && apt-get upgrade -y && ...
=> CACHED [3/4] ADD . /
=> CACHED [4/4] RUN uv sync
=> exporting to image
The per-layer view, useful for both caching and size questions:

$ docker image history simple-translate
IMAGE          CREATED       CREATED BY                                      SIZE
484239a9b64d   28 hours ago  CMD ["/bin/bash"]                               0B
<missing>      28 hours ago  ENTRYPOINT ["uv" "run"]                         0B
<missing>      28 hours ago  RUN ... DEBIAN_PACKAGES=build-essential curl    26.9MB
<missing>      28 hours ago  COPY --chown=app:app . ./ # buildkit            1.25MB
<missing>      28 hours ago  WORKDIR /app                                    4.1kB
<missing>      28 hours ago  USER app                                        0B
<missing>      28 hours ago  RUN ... (apt + pip + uv + useradd)              396MB
<missing>      28 hours ago  ENV UV_PROJECT_ENVIRONMENT=/home/app/.venv      0B
Metadata-only instructions (ENV, WORKDIR, USER, CMD, ENTRYPOINT, ARG) cost 0B; RUN and COPY are where size lives. Example layer stack for the course's image: Debian Linux kernel base → install Python & pip → upgrade pip → install uv → uv sync.

Note — Disk-space scenario

You debugged all week without --rm. docker container ls shows nothing running, yet docker system df shows containers eating disk. Cause: exited containers are still on disk, each keeping its writable layer. docker container ls -a lists them; docker system prune -a (or docker container prune for just containers) reclaims the space. It is not the build cache (that is a separate docker system df row, cleared by docker builder prune), and docker run does not create untagged images.

Mounts: why containers forget, and the three fixes
Containers are ephemeral: the container filesystem is a writable layer, so changes are discarded when the container exits — and with --rm the layer is deleted outright. Two needs follow: (1) development — edit code on the host and see it live inside the container; (2) persistence — keep models and outputs after shutdown. Mounts link host directories or Docker-managed storage into the container.

Type	Who picks the location	Persists?	Typical use
Bind mount	You (a host path)	Yes, but only on the host	Source code, config, secrets (dev)
Named volume	Docker	Yes (Docker-managed)	Database files, model artifacts
tmpfs	— (RAM)	No	Ephemeral secrets / scratch
Note — The slash rule

With -v, Docker decides bind mount vs named volume by whether the source contains a /:
docker run -v "$(pwd)":/app app → source has a slash → bind mount, you control the host location.
docker run -v appdata:/data app → no slash → named volume, created if needed, Docker manages the storage.
Both persist after exit; the difference is who owns the location. Always give an absolute host path — $(pwd) is the reliable way.

Named volume commands: docker volume create mydata, then docker run -v mydata:/data transcribe-audio; manage with docker volume ls / inspect / rm. Volumes persist after the container is removed and can be mounted by several containers at once.
Read-only: append :ro, e.g. -v "$(pwd)/secrets":/secrets:ro — least privilege for files.
-v vs --mount: -v is the terse legacy form; --mount is explicit and safer:
--mount type=bind,source="$(pwd)",target=/app
--mount type=volume,source=mydata,target=/data
Gotcha: if the bind source is missing, --mount errors loudly, while -v silently creates an empty directory.
When to use which: bind mount → live code, config, secrets in dev; named volume → persistent/shared data; tmpfs → ephemeral secrets.
Lecture 3 · Containers II

Architecture, lean images, Compose, and ports
Sources: L03 Containers II; Tutorial 5 (mega-pipeline); the gateway/processor demo that becomes the port_toy tutorial.

Monolithic vs microservice architecture
The running example is an online cheese store. The monolith: browser and mobile apps talk over HTML / REST / JSON to one Java server holding the Storefront UI, Catalog, Reviews and Orders modules, backed by one Oracle database. The microservice version: an API service fronting independent Storefront UI, Catalog, Reviews, Orders and Recommendation modules, each with its own store — databases, cloud storage, models — all speaking REST/JSON.

Note — Four terms the slides deliberately separate

HTML is markup (HTML is HTML). JSON is the data format exchanged between clients and APIs. REST is an architectural style for APIs. HTTP is the communication protocol underneath.

Monolith	Microservices
Development	<span class="yes">+</span> Simplicity — most tools and IDEs natively support monolithic apps	<span class="no">−</span> Development and deployment complexity — multiple technologies and diverse dependencies need a more intricate setup
Deployment	<span class="yes">+</span> Ease of deployment — all components in a single unified package, so there is little to coordinate or orchestrate	<span class="yes">+</span> Streamlined patching — update one service without touching the rest
Scaling	<span class="yes">+</span> Easier to scale by replicating the entire application (horizontal scaling)	<span class="no">−</span> Scaling the whole application is intricate because components are disparate
Maintenance	<span class="no">−</span> Complexity grows over time; harder to change or locate issues	<span class="yes">+</span> Simplified maintenance — modular design is easier to manage, update, debug
Failure	<span class="no">−</span> System vulnerability — one component failing can collapse the whole system	<span class="yes">+</span> Fault isolation — a failure in one service need not bring down the app
Patching	<span class="no">−</span> Cumbersome — tightly-coupled components	<span class="yes">+</span> Per-service patching
Technology	<span class="no">−</span> Technology lock-in — interdependencies make adoption or upgrades hard	<span class="yes">+</span> Technological flexibility — services are independent
Startup	<span class="no">−</span> Slow — all components initialize simultaneously	<span class="yes">+</span> Quick — components initialize in parallel
Onboarding	<span class="no">−</span> New developers must learn the entire codebase	<span class="yes">+</span> Learn one service
Watch out — The traps in this table

Three microservice benefits are routinely offered as monolith benefits: fault isolation, independent deployment of modules, and easy technology adoption. All three are <span class="no">wrong for a monolith</span>. The genuine monolith arguments are: simple development with standard tooling, one deployable unit so there is nothing to orchestrate, and scaling by replicating the whole app. Note also the deliberate asymmetry: the slides list Scalability as a monolith advantage and scaling as a microservices disadvantage.

Then vs now: a decade ago apps were monolithic, built on a single stack (.NET or Java), long-lived, deployed to a single server. Today they are constantly developed, built from loosely coupled components, deployed often, to a multitude of servers — and in data science they integrate various data types, sources and models. Microservices at scale → Docker + Kubernetes.

The development workflow, without and with Docker
Without Docker: every developer machine needs OS-specific installs (Windows: Node.js + Python; Linux: C++ + Python; Mac: Node.js + Python); everyone pushes to GitHub; the build server must be configured with all necessary software and frameworks; the production server must have them too, and typically runs a different OS version than any dev machine. (Node.js = a platform for running JavaScript outside a browser.)

With Docker: dev machines need only Docker; containers are set up once; everyone pushes code to source control; the build server needs only Docker and builds images for a release, pushing them to a container registry; the production server needs only Docker and pulls images from the registry and runs them.

Team workflows
Scenario	How it runs
1 — early development	A “senior” developer writes the Dockerfile plus the initial pyproject.toml and uv.lock and pushes them to GitHub. Everyone pulls those files, builds the image themselves, runs containers, develops inside them, may install packages (changing the uv files) or edit the Dockerfile, and rebuilds. Work is submitted as pull requests including any Dockerfile/uv changes; the senior dev reviews, merges and consolidates into a new Dockerfile and uv files.
2 — later development	The senior dev builds the images and pushes them to Docker Hub, with Dockerfile and uv files on GitHub. Developers pull images from DockerHub and the files from GitHub, run containers and develop inside them; rebuilding is rare. PRs carry code and occasionally Dockerfile/uv changes; the senior dev merges, consolidates, rebuilds and pushes new images.
Is there a perfect workflow? No. Clear communication and rules are essential; each team can have its own workflow based on project and team needs.

Build optimization
Why bother: every deploy is a download (push to the registry, pull on each server before it can start); more packages means more to secure and patch, and build tools and secrets should not ride along; slow builds tax the whole team because every code change means rebuild → push → pull; storage and bandwidth are not free — one fat image × every version × every server. The slogan: ship only what you need to RUN, and keep what changes small.

1. Layer caching — order matters
Each instruction is a cached layer; change one and you bust the cache for every layer after it. So put rarely-changing steps first, frequently-changing steps last. Classic mistake: COPY . . before installing dependencies, so every code edit reinstalls everything.

COPY pyproject.toml uv.lock ./   # deps change rarely → copy them first
RUN uv sync                      # cached until your dependencies change
COPY . .                         # the only layer that re-runs on a code edit
2. .dockerignore — shrink the build context
Like .gitignore, but for the build context Docker sends to the daemon. Each line is a pattern excluded from the context. Smaller context = faster builds, and you cannot accidentally bake secrets or junk into the image.

.git             # repository history — metadata, not needed to run
__pycache__/     # compiled Python bytecode caches
.venv/           # local virtual environment — rebuilt inside the image
node_modules/    # installed JS packages — reinstalled in the image
secrets/         # credentials & keys — must never enter the image
*.csv            # bulky local data files — not needed at build time
3. How Python packages install — and why the base image matters
Prebuilt wheel (.whl) — a ZIP archive containing a ready-to-install package; pip just extracts and unpacks it. No compiler needed. Most packages, including NumPy and pandas.
Source distribution (sdist) — an archive of source code (Python, C, or Rust). If no wheel matches your platform, pip extracts it, builds a wheel, then installs that. C/Rust extensions require a build toolchain.
File-name shapes: cheese_utils-1.0.tar.gz (sdist, contains pyproject.toml, src/, tests/) vs cheese_utils-1.0-py3-none-any.whl (wheel, contains the package plus *.dist-info/ with METADATA, WHEEL, RECORD).
Base image	Approx. size	When to use it
python:3.14	~1.63 GB	Rarely — build tools included (gcc, g++, make), so it can compile from source
python:3.14-slim	~217 MB	The default — enough when your dependencies have wheels
python:3.14-alpine	~86 MB	Smallest, but musl libc means often no matching wheel, so it compiles from source. Only when you know what you're doing
Smaller base → fewer known vulnerabilities (CVEs). The course's own images use python:3.12-slim-bookworm.

4. Fewer, leaner layers
Layers are additive: files deleted in a later layer still take up space in the earlier one. A separate cleanup layer does not shrink the image — chain related commands and clean up in the same RUN with &&.

FROM python:3.14-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends build-essential \
 && rm -rf /var/lib/apt/lists/*
Trim the extras: --no-install-recommends for apt (the only one L04 keeps), --no-cache-dir for pip, apt-get clean. build-essential = the common C/C++ build tools needed by dependencies built from source. Note the nuance: deleting the downloaded package lists in the same RUN saves space, while the installed build tools remain in the image — which is what multi-stage builds fix.

5. Multi-stage builds
Build in one stage, copy only what the app needs into the final stage; build tools stay out of the final image.

FROM python:3.14 AS builder          # builder: full image, has build tools
WORKDIR /app
RUN pip install uv
COPY pyproject.toml uv.lock ./
RUN uv sync                          # installs dependencies into .venv

FROM python:3.14-slim AS runtime     # runtime: slim, only what's needed to run
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY . .
CMD ["/app/.venv/bin/python", "app.py"]
6. Measure it — do not guess
docker images — the total size of each image.
docker history <image> — per-layer size; find the fat layer.
7. Building for the target platform
Docker build already uses Buildx and BuildKit. Choose the platform where the app will run, not your laptop's: Apple Silicon = arm64, Intel/AMD = amd64, clouds are either — check the deployment target.

$ docker build --platform linux/amd64 -t myapp --load .     # L03; L04 drops --load
$ docker build --push --platform linux/amd64,linux/arm64 -t myapp .
--platform targets the CPU architecture; --load puts the image into your local Docker (the default, and the L04 version of this slide simply omits the flag); --push pushes a multi-platform image to a registry. The course's docker-build-push.sh does this with docker buildx create --driver-opt network=host --use --name multi-arch then docker buildx build --platform linux/amd64,linux/arm64 --push -t $DOCKER_USERNAME/$IMAGE_NAME -f Dockerfile .

Build secrets
When a RUN step needs a token, supply it through a temporary secret mount so the token stays out of the Dockerfile and the image.

# syntax=docker/dockerfile:1        ← enables --mount; must be the FIRST line
RUN --mount=type=secret,id=gh_token \
    GH_TOKEN=$(cat /run/secrets/gh_token) && \
    pip install "git+https://GH_USERNAME:${GH_TOKEN}@github.com/org/lib"

$ docker build --secret id=gh_token,src=$HOME/.gh_token .
The id is the link between the RUN --mount and the --secret flag; /run/secrets/<id> is a container path mounted only for that build step; src= is the local token file.

Anti-pattern	Risk for secrets
ENV GH_TOKEN=ghp_xxx	Stored in the image configuration
ARG GH_TOKEN	May appear in history or build metadata
COPY .gh_token /tmp/token	Remains in an earlier layer even after later deletion
Docker Compose
The problem: a real app is many containers, and by hand that is one docker run per service with its own -p, -v, -e, --network flags; you create the network and start services in the right order yourself; and every code change is stop → remove → rebuild → run, service by service.

docker network create app-net
docker build -t processor-img ./processor
docker run -d --network app-net --name processor processor-img
docker build -t gateway-img ./gateway
docker run -d --network app-net -p 8090:9100 \
  -e PROCESSOR_HOST=processor -e PROCESSOR_PORT=9200 \
  -v "$PWD/gateway:/app" gateway-img
What Compose is: one tool plus one file to define and run a multi-container app. One file — compose.yaml (legacy name docker-compose.yaml) describes every service, network and volume. One tool — docker compose, built into Docker. You state the end result; Compose builds, creates and starts it.

Task	By hand	With Compose
Network	docker network create + attach each container	Automatic, shared
Start it all	N × docker run, in order	docker compose up
Tear down	stop + rm each	docker compose down
services:
  gateway:
    build: ./gateway                  # build from ./gateway/Dockerfile
    ports:
      - "127.0.0.1:8090:9100"         # ip:host:container
    volumes:
      - ./gateway:/app                # bind mount (host path)
      - ./secrets:/secrets:ro         # read-only
      - models:/models                # named volume
    environment:
      PROCESSOR_HOST: processor       # like -e
      PROCESSOR_PORT: "9200"
    env_file:
      - .env                          # keep secrets out of the YAML
    depends_on:
      processor:
        condition: service_healthy
  processor:
    image: ac215/processor:1.0        # pull a prebuilt image instead of building
    healthcheck:
      test: curl -f localhost:9200/health
volumes:
  models:                             # declare the named volume
One service per entry, and the service name is its hostname on the Compose network.
build: — Compose builds an image from that directory's Dockerfile and local files. image: — pull a prebuilt image from a registry such as Docker Hub. Each service picks one.
ports ↔ -p, volumes ↔ -v, environment ↔ -e.
Volumes, left side: ./secrets:/secrets:ro is a host folder you chose (bind mount); models:/models is a named volume Docker owns. Same source:container shape, two different meanings.
Networking for free: docker compose up auto-creates the project network, attaches both containers and registers each under its service name in DNS — so http://processor:9200 works with no docker network create and no IPs.
depends_on and what it actually guarantees
Plain depends_on: [processor] only guarantees order: processor comes “up” first, then gateway. But “up” = container started, not app ready. For real readiness, add a healthcheck to the dependency and a condition to the dependent. The three fixed condition values (not names you invent):

Condition	Meaning
service_started	Default behavior — the container has started
service_healthy	Wait until the dependency's healthcheck passes
service_completed_successfully	Wait until the dependency exits with success (one-shot jobs)
Everyday Compose commands (run from the directory holding the compose file)
Command	What it does
docker compose up	Build images, create the network, start every service
docker compose up -d	Same, detached in the background
docker compose up --build	Rebuild the images first
docker compose ps / ps -a	Which services are up / also which have stopped
docker compose logs -f	Every service's output live, in one stream (logs -f gateway for one)
docker compose exec gateway sh	Run a command / open a shell inside a running service
docker compose down	Stop and remove all containers and the network — the true inverse of up. Built images remain
docker compose down -v	Also delete named volumes — your data. Destructive
Ctrl+C only stops containers; they remain in exited state (visible with docker compose ps -a) and the network still exists, which is why you also run down. A stopped container has already released its port binding, so down is about not leaving containers and networks behind, not about freeing the port.

Aspect	Docker Compose	Kubernetes
Scope	One machine	Many machines (a cluster)
Great for	Dev and a single small server	Production scale, self-healing, rolling updates
Compose has no multi-machine scaling, self-healing, rolling updates or cross-node load balancing — production multi-host means Kubernetes, which keeps the same “declare services, find them by name” idea.

Where a variable lives decides when it exists
Where you write it	Compose file (${VAR})	Build	Image	Container (run)
Dockerfile ENV	—	✓	✓	✓
Dockerfile ARG	—	✓	—	—
Compose build.args	—	✓	—	—
Compose environment: / env_file:	—	—	—	✓
.env file (auto-loaded)	✓	—	—	—

So TAG=1.0 in .env (or export TAG=1.0 in the shell) fills image: ac215/processor:${TAG} in the compose file — substitution happens when Compose reads the YAML, not inside the container.

Networking and ports
Containers are isolated by default — each has its own network namespace (Lecture 2) until you wire two paths: (a) service → service and (b) your browser → the app.

(a) Container to container: one shared network, reached by name
1. docker network create app-net
2. docker run --network app-net --name gateway   gateway-img
   docker run --network app-net --name processor processor-img
3. POST http://processor:9200/        ← Docker DNS, no IP anywhere
--name is the DNS name — and only the container being dialed needs one (the L04 diagram labels the gateway http://gateway:9100 and notes it is optional, since nothing calls the gateway by name). On a user-defined network Docker resolves container names automatically; drop --network app-net and both land on the default bridge network, where name resolution does not work. Compose does all three steps for free.

(b) Outside to container: publish a port
docker run --network app-net --name gateway -p 127.0.0.1:8090:9100 gateway-img
# compose:  ports: ["127.0.0.1:8090:9100"]
#
#  8090      :      9100
#  HOST      :      CONTAINER
What you see	What it means
"8090:9100"	host:container — port 8090 on your laptop forwards to 9100 inside the container
"127.0.0.1:8090:9100"	ip:host:container — same, but only this machine may connect (loopback)
127.0.0.1:8090->9100/tcp	The mapping as docker ps reports it. Left of -> is the host
0.0.0.0:8090->9100/tcp	What you get with no IP — every address, so others on the same wifi can reach it
No ports: / no -p	Container is internal only — reachable on the network, invisible to your laptop. Listening is not enough
EXPOSE 9100 in a Dockerfile	Documentation only. It publishes nothing; you still need -p
localhost inside a container	That container itself — not your laptop, not another container
http://processor:9200	Another container by service name, resolved by Docker's DNS
Listening port (9200)	Stable, you configure it, a server waits there
Source port (44456)	Ephemeral, picked by the OS per outgoing connection, discarded afterwards — different every time
port is already allocated	Two containers tried to publish the same host port. Change the left number
Connection refused	Something is listening somewhere, but not at the address you dialed
could not resolve host	The name is wrong, or the containers are not on the same user-defined network
Note — Why the host side is the one you change

Two projects can both listen on 9100 inside their own containers with no conflict, because each has its own network namespace. They cannot both publish to 8090 on your laptop. Published host ports are the scarce resource. And a port number is a contract: it appears twice — where the server binds it (PORT) and where the caller dials it (PROCESSOR_PORT). Both sides must agree. Keep them in the compose file, never hardcoded in the code.

The flexible part: four modes in one script
docker-shell.sh exists because the docker build/docker run commands now have to juggle multiple architectures, mounted volumes, environment variables and secrets — wrapping that in a script keeps the workflow consistent across Mac, Linux and Windows. The name of the branch is these four modes:

Command	Mode	What it does
./docker-shell.sh	dev-run (default)	Build the image locally, then run it
./docker-shell.sh dev	dev	Build the local image only, no run
./docker-shell.sh run	run	Run without building — uses the local image if docker image inspect finds it, otherwise falls back to $DOCKER_USERNAME/$IMAGE_NAME from the registry
./docker-shell.sh prod	prod	Remove any existing multi-arch builder, docker buildx create --driver-opt network=host --use --name multi-arch, then docker buildx build --platform linux/amd64,linux/arm64 --push
These map onto the two team workflows from the lecture: early development = everyone pulls the Dockerfile and uv.lock and builds locally (dev); later development = a senior dev publishes images (prod) and most devs just run. chmod +x docker-shell.sh if it is not executable yet. Note — The credentials change, and why it matters

Tutorial 5's Dockerfile baked ENV GOOGLE_APPLICATION_CREDENTIALS=secrets/mega-pipeline.json into the image, and the key lived in each component's own secrets/ folder inside the repo. This branch does neither: the Dockerfile sets no credentials variable, and docker-shell.sh passes it at run time with -e while bind-mounting a secrets/ folder that sits one level above the repo at /secrets. Note also that the path is now absolute (/secrets/mega-pipeline.json), where Tutorial 5's was relative. Keeping the folder outside the repo is the canonical way to make committing it impossible — the practice Lecture 3 said the course would "move toward".

port_toy — the compose/ports demo (assigned in Lecture 4)
Two containers: gateway serves the page and forwards your text; processor upper-cases it and replies.

browser --localhost:8090--> gateway --http://processor:9200--> processor
            (published)      (serves page)     (by name, internal only)
docker compose up does four things: reads the YAML and builds an image per service, creates a private network (port_toy_default), starts both containers on it, and registers each under its service name in that network's DNS.

$ docker compose ps
NAME                   SERVICE     STATUS    PORTS
port_toy-gateway-1     gateway     Up        127.0.0.1:8090->9100/tcp
port_toy-processor-1   processor   Up                                   ← empty: never published

$ curl localhost:8090                                   → the HTML page          OK
$ curl --max-time 3 localhost:9200/health               → Connection refused     FAIL
$ docker compose exec gateway curl http://processor:9200/health   → ok            OK
$ docker compose exec gateway curl http://localhost:9200/health   → refused       FAIL
Those four commands carry two lessons: processor is a hostname registered by Compose, and localhost inside a container is that container — the single most common cause of “it works on my machine but the container can't reach it”. The gateway image installs curl on purpose and the processor's does not: install a package only in the image that needs it.

Doing it without Compose is exactly the four steps above by hand: docker network create toynet; docker build -t toy-processor ./processor; docker run -d --name processor --network toynet -e PORT=9200 toy-processor (no -p, internal only); docker run -d --name gateway --network toynet -p 127.0.0.1:8090:9100 -e PROCESSOR_HOST=processor -e PROCESSOR_PORT=9200 toy-gateway. Clean up with docker rm -f gateway processor and docker network rm toynet.

Reference · Distractor debunk

Statements that sound right and are wrong
Tempting claim	Why it is wrong
“A hypervisor is a kernel module the guest OS loads to translate syscalls.”	That describes nothing real here; the hypervisor sits below the guest and presents virtual hardware. Syscall translation is what the thin Linux VM does for Docker on Mac/Windows
“A hypervisor is a user-space emulator that interprets each guest instruction.”	That is an emulator (e.g. QEMU in pure emulation). A hypervisor virtualizes rather than interprets instruction by instruction
“A container includes its own OS kernel.”	A container is the user space; it shares the host kernel. Only a VM has a guest kernel
“Activating a venv replaces the system Python interpreter.”	It only prepends the env's bin/ to PATH. The system interpreter is untouched
“Activating changes which packages are installed, not how Python is found.”	Backwards — uv sync installs; activate changes lookup
“which reports the interpreter available when the shell started.”	which searches PATH now, which activation just changed
“RUN steps are cached and COPY/ADD always rebuild.”	Caching depends on inputs changing, not on the instruction keyword
“Docker caches only layers inherited from the base image.”	Every instruction produces a cacheable layer
“Docker keeps one cached layer per image, for the most expensive step.”	Invented. The cache is per layer, invalidated from the changed step onward
“CMD is baked in and cannot be overridden at run time.”	Overriding CMD is exactly what trailing docker run arguments do
“A run argument replaces the whole startup command including ENTRYPOINT.”	Only --entrypoint does that
“Exited containers are hidden because they are detached; stopping them frees their layers.”	They are hidden because ls shows only running ones; their writable layers persist until removed
“Each docker run creates an untagged image.”	run creates containers. Untagged (dangling) images come from rebuilds
“A monolith isolates faults between modules.”	The opposite — one component failing can collapse the whole system. Fault isolation is a microservice benefit
“A monolith lets each module deploy independently.”	It deploys as one unified package — which is its real advantage, phrased honestly
“A monolith adopts new technology easily.”	Technology lock-in is a listed monolith disadvantage
“A cleanup RUN rm -rf ... in a later layer shrinks the image.”	Layers are additive; delete in the same RUN that created the files
“Alpine is always the right base because it is smallest.”	musl libc means many wheels do not match, so pip compiles from source — slower builds, needs a toolchain
“.dockerignore deletes files from the image.”	It excludes them from the build context sent to the daemon in the first place
“EXPOSE 9100 publishes the port.”	Documentation only; you still need -p or ports:
“-p 9100:8090 is the same as -p 8090:9100.”	It is always host:container. Reversing it is the most common Docker networking mistake
“A container reaches another at http://localhost:9200.”	localhost is that container's own loopback. Use the service/container name
“Container names always resolve.”	Only on a user-defined network; the default bridge has no DNS for names
“depends_on waits until the service is ready to serve traffic.”	It waits until the container has started; readiness needs a healthcheck + condition: service_healthy
“docker compose down is needed to free the published port.”	A stopped container has already released it; down removes containers and the network
“Compose can scale the app across machines.”	Compose is single-machine; that is Kubernetes
“Compose environment: values are available during the build.”	They exist only in the running container; build-time needs ARG / build.args
“An API key is the right way for a container to authenticate to GCP.”	Lightweight and less secure; server-to-server automation uses a service account
Worked · The six sample questions

Sample questions, answered with the reasoning
1. Which best describes the role of a hypervisor in a VM setup?

Answer

A software layer that creates and manages VMs, each running its own full guest OS on virtualized hardware. The other three describe a kernel module, a container runtime, and a user-space instruction emulator — none of which is a hypervisor.

2. which python shows /usr/local/bin/python; after activating a virtual environment, what does she see and why?

Answer

A path inside the virtual environment, because activation puts the environment's bin/ directory earlier on PATH. Not “replaces the system interpreter” (nothing is replaced), not “same path” (the lookup did change), and which resolves against the current PATH, not the shell's startup state.

3. ENTRYPOINT ["/bin/echo","Hello"] + CMD ["world"]; what does docker run -ti greeter Pavlos print?

Answer

Hello Pavlos — the run argument replaces CMD and is appended to ENTRYPOINT. This is the exact slide example from Lecture 2.

4. Dependencies installed, then source copied. After changing one source file, why is the dependency step cached while the copy and later steps rebuild?

Answer

Because the dependency step's inputs are unchanged, while changing the copied source invalidates that step and everything after it. Caching keys on inputs, not on whether the instruction is RUN or COPY, and it applies to layers the Dockerfile creates as well as inherited ones.

5. No --rm all week; nothing running, but docker system df shows containers using disk. What is happening and how do you reclaim it?

Answer

Exited containers are still on disk; docker container ls -a lists them and docker system prune -a clears them. Build cache is a different row (cleared by docker builder prune); detached containers do appear in container ls; and docker run creates no images.

6. A Java monolith cheese store — which consideration is a genuine argument for leaving it as it is?

Answer

A monolith deploys as one application, reducing the need to coordinate and orchestrate multiple independently deployed services. Fault isolation, independent module deployment and easy technology adoption are all microservice advantages misattributed to the monolith.

Review · 32 questions with answers

Self-test
Cover the green blocks and work down the list. These are written in the same style as the samples, and every answer is derived from the sections above.

1. Which Linux kernel feature makes two containers able to have a process with PID 1 each?

Answer

The PID namespace — each namespace numbers from 1; the host sees distinct global PIDs (e.g. 345 and 678).

2. A container runs a process as root. What privileges does that process have on the host?

Answer

Non-root. The user namespace maps it to an unprivileged host user.

3. One container is running an infinite memory allocation. Which feature stops it from taking down the host?

Answer

cgroups — they limit and manage CPU, memory, disk I/O and network bandwidth. Not namespaces, and not AppArmor/SELinux.

4. Roughly how many syscalls does Docker's default seccomp profile block, out of how many?

Answer

44 blocked out of 300+. Examples: reboot, quotactl.

5. Why can a Linux-kernel-dependent container run on macOS?

Answer

The OS spins a stripped-down Linux VM that translates syscalls from the Docker daemon to the native kernel — HyperKit on macOS, WSL2 (a custom Linux kernel integrated with Windows) on Windows.

6. Which container engine is daemonless and supports rootless execution?

Answer

Podman. LXC is the original but less isolated; rkt is security-focused and composable; OrbStack is macOS-only.

7. In the recipe analogy, which piece is the image?

Answer

The pre-assembled ingredient kit. Dockerfile = recipe, container = the cooked dish. In OOP terms: image = class, container = instance.

8. What gets added when you launch a container from an image?

Answer

A writable layer on top of the read-only image layers. Everything below is immutable.

9. Which Dockerfile instruction can fetch a URL and auto-extract an archive?

Answer

ADD. COPY does neither.

10. You need a variable during the build but absent from the final image. Which instruction?

Answer

ARG (or Compose build.args). ENV would persist into the image and the container. Neither is safe for secrets — use RUN --mount=type=secret with --secret id=,src=.

11. What does docker build -t app -f Dockerfile . do with the final .?

Answer

It sets the build context to the current directory — the files sent to the daemon and available to COPY/ADD. .dockerignore filters exactly this.

12. Your image is 480 MB and you want to know which step is responsible. Which command?

Answer

docker history <image> for per-layer sizes; docker images for the total.

13. Reorder these for best caching: COPY . ., RUN uv sync, COPY pyproject.toml uv.lock ./.

Answer

COPY pyproject.toml uv.lock ./ → RUN uv sync → COPY . .. Rarely-changing steps first; code last, so a code edit re-runs only the final layer.

14. Does adding RUN rm -rf /var/lib/apt/lists/* as its own instruction shrink the image?

Answer

No. Layers are additive — the files still occupy the earlier layer. Delete in the same RUN that created them, chained with &&.

15. Which base image is the recommended default, and what makes alpine risky?

Answer

python:3.14-slim (~217 MB) when dependencies ship wheels. Alpine (~86 MB) uses musl, so wheels often do not match and pip builds from source, needing a toolchain — L04 adds that wheel compatibility depends on the environment, so alpine may need different wheels from the full and slim images. Full python:3.14 is ~1.63 GB.

16. What is the point of a multi-stage build?

Answer

Install with build tools in a builder stage, then COPY --from=builder only the artifacts (e.g. /app/.venv) into a slim runtime stage, so compilers never ship.

17. You are on an M-series Mac deploying to an Intel cloud VM. What does the build need?

Answer

--platform linux/amd64 (your laptop is arm64). --load puts it in local Docker; --push with a comma-separated platform list publishes a multi-platform image.

18. Your container exits instantly, so docker exec has nothing to attach to. How do you get a shell?

Answer

docker run -it --entrypoint /bin/bash <image>. Remember: exec attaches to a running container, run starts a new one.

19. Which docker inspect keys confirm a volume mounted, an env var set, and a port published?

Answer

Mounts, Config.Env, NetworkSettings.Ports.

20. docker run -v mydata:/data app versus docker run -v "$(pwd)":/data app — what differs?

Answer

No slash in the source → named volume, Docker-managed storage, created if absent. A slash → bind mount of that host directory. Both persist after exit; the difference is who owns the location.

21. You typo a bind-mount source path. What happens with -v versus --mount?

Answer

-v silently creates an empty directory; --mount errors loudly. That is the argument for --mount.

22. Why does the mega-pipeline tutorial run docker run --rm -ti -v "$(pwd):/app" transcribe_audio?

Answer

The bind mount is the dev loop: edit on the host in VS Code and the change is live inside the container — and uv add run inside writes the updated pyproject.toml back to the host. Rebuild afterwards to bake the deps in.

23. In the mega-pipeline, how do the five services communicate, and why not by API?

Answer

Indirectly, by writing outputs to a shared GCS bucket (mega-pipeline-bucket) that the next stage reads — because APIs have not been covered yet. Production microservices would call each other directly over REST/JSON.

24. Which two components need no --upload step, and why?

Answer

synthesis_audio_en and synthesis_audio — synthesis writes the .mp3 directly to GCS, no local file.

25. Which GCP authentication method suits a container doing server-to-server automation with no human present?

Answer

A service account (part of IAM), pointed at by GOOGLE_APPLICATION_CREDENTIALS. OAuth 2.0 is user-driven; API keys are lightweight and less secure; Workload Identity Federation is for external identities.

26. What keeps the service-account key out of GitHub, and what is the better long-term practice?

Answer

A .gitignore entry for secrets/; the canonical practice is keeping the secrets folder outside the repo entirely. Also add secrets/ to .dockerignore so it cannot be baked into an image.

27. Two services in one compose file; only one has a ports: entry. Can you curl the other from your laptop?

Answer

No — without a published port it is internal only, reachable as http://<service>:<port> from inside the network. Listening is not the same as published.

28. docker ps shows 0.0.0.0:8090->9100/tcp. What does that mean, and how would you restrict it?

Answer

Host port 8090 on every address forwards to container port 9100 — anyone on the same wifi can connect. Restrict with "127.0.0.1:8090:9100" (ip:host:container).

29. Two Compose projects both fail with port is already allocated. Which number do you change?

Answer

The host (left) number. Container ports never collide — each container has its own network namespace.

30. You run two containers without --network and one cannot resolve the other's name. Why?

Answer

They landed on the default bridge network, where name resolution does not work. Create a user-defined network and attach both; --name then becomes the DNS name. Compose does this automatically.

31. Your gateway starts before the processor can serve traffic even though depends_on is set. Fix it.

Answer

Add a healthcheck to the processor and depends_on: {processor: {condition: service_healthy}}. Plain depends_on only guarantees the container started. The other conditions are service_started and service_completed_successfully.

32. What does docker compose down -v destroy that docker compose down does not?

Answer

Named volumes — your persisted data. Plain down removes containers and the network and leaves built images alone.
